## 第一轮测量与优化依据

**缩小 EEPROM 读取范围，复用静态状态。** 优化前代码在 `8311/tools.lua` 与控制器中各读取 256 字节，实际动态指标只使用偏移 96–105，模块静态信息只用到前 60 字节。目标设备只读计时，每项 5 次：

| 操作 | 平均耗时 |
| --- | --- |
| EEPROM 51：256 字节 | 39.11 ms |
| EEPROM 51：106 字节 | 16.28 ms |
| EEPROM 51：定位偏移 96，仅读 10 字节 | 1.99 ms |
| EEPROM 50：256 字节 | 38.49 ms |
| EEPROM 50：60 字节 | 9.31 ms |

将读取长度改为 106 和 60 字节，两项独立计时的均值合计从约 77.6 ms 降为 25.6 ms；进一步对动态指标定位后仅读 10 字节，合计约 11.3 ms。后者五次均成功返回 10 字节，证明当前驱动支持此读取方式。这些数字仅衡量 EEPROM 读取开销，不能当作整页加速或功耗降幅。实现时仍需检查短读、定位失败、读取失败，并测试地址偏移和数据解析，保留已有缺失值处理。`nixio.File` 提供定位和指定长度读取接口。[nixio 文件接口文档](https://openwrt.github.io/luci/api/modules/nixio.File.html)

现有 CN 的 `tools.metrics()` 热调用约 66 ms；`action_gpon_status()` 首次约 581 ms，随后约 265–287 ms。单项计时显示，模块类型查询约 37 ms、启动分区约 52 ms、OLT 厂商查询约 66 ms。模块信息可缓存并在相关配置更改时失效；启动分区可直接解析 `/proc/cmdline`；OLT 信息应根据注册状态和有效期更新。动态读数可采用短期共享缓存，同时返回采样时间和过期状态，避免多个页面重复读硬件。

实际 HTTPS metrics 请求在同一连接上的热请求约 238–253 ms，首次约 696 ms，包含网络/TLS/Web 栈开销。受保护的完整状态 HTTP 接口返回 403，所以完整状态数字来自 SSH 下直接调用其只读生成函数，不能当作已登录整页耗时。

**减少重复轮询和进程创建。** RX_LOS 禁用分支每秒通过外部 `cat` 读 GPIO，可以先用 shell 内建读取保持原周期与行为。状态页面隐藏时可暂停其自身刷新。VLAN、配置和 Hook 采用变更通知与合并处理；保留重新注册后的修正规则。当前 `sfp_i2c`、`omcid`、RX_LOS 脚本各自占用很低，省掉必要服务不会带来已证实的大幅降温收益。

CN 当前 OMCI stdout/stderr 已开启，但采样期间 `logd` 不是 CPU 热点。调试输出可以做成按需开启、限频并保留错误日志的选项，实际收益需要联网后测日志量，不能从“已开启日志”直接推导为主要热源。

## 降温实验的边界

固定最高频率值得评估。Linux 的 `performance` 请求策略允许的最高频率，动态策略则按负载选择频率；具体节能效果仍取决于驱动与硬件。[Linux CPUFreq 文档](https://docs.kernel.org/admin-guide/pm/cpufreq.html#performance)

建议把 `conservative` 作为后续可恢复的临时 A/B 实验，比较空闲与网页访问的响应、温度和频率驻留，再在接入光纤后验证注册、吞吐、丢包和 IPTV。保持默认策略，直到有对应业务证据；当前没有测得可承诺的降温度数。设备的 thermal 保护阈值也不能代替整支光模块的长期工作温度规范。

散热方面，当前没有额外风道，可先用现有风扇做相同位置、相同负载、相同室温的对照，等待温度趋稳后比较。软件减少 CPU 工作无法消除光学器件、供电和高速接口自身的功耗，软硬件两方面需要分别验证。
